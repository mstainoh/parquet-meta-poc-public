# CLAUDE.md

Guidance for Claude Code in this repo: rules for answering, coding and testing, what the
project is, its architecture.

## Rules for answering
- Architecture first. Do NOT decide architecture rules on the fly: if a change is not
  obvious, check first. If choosing an implementation strategy is part of the prompt,
  explain what will be done and ask for confirmation.
- Once the change is clear, implement only the code; a minimum check is enough (e.g. a quick
  dummy run), not a full suite. Then summarize to the user what was done and tested.
- Do not commit automatically: ask for confirmation (a commit message preview is fine).
  Before committing, do the cleanup:
  - an architecture change is discussed first; with approval it can go to the ADR;
  - if the package's public behaviour changed, add it to `CHANGELOG.md`;
  - a new markdown file is registered (see "Reference documents").

### Testing
Run `pytest` from the repo root (config in `pyproject.toml`, tests in `tests/`) when code
changes or the user asks; not for documentation or comments. The viewer has no automated
tests: it is checked by hand in the browser.

### How to create code
- Functional coherence: no polymorphism unless needed or practical (`str | Path` is ok,
  `str | Path | dict` is not). Docstrings in numpy style.
- Language: code, identifiers, docstrings, logs, messages and the public entry files
  (`README.md`, `CHANGELOG.md`, `.env.example`, the example datasets' docs) in **English**; docs
  under `docs/` in **Spanish**. Follow the file you are writing into.
- Examples, test data and comments in public files: **talking about mining is fine, talking
  about the company is not.** Prefer generic mining tables (wells: `well_id, lat, lon, name,
  permit_name`; water levels: `well_id, datetime, level_m, stick_up_m`; submersible pumps:
  `pump_model, manufacturer, nominal_power, ...`) with obviously fake IDs (`W-999`). Never
  point at the company's own data or site: no company/project name, real table names, real
  IDs, coordinates or the actual deposit. Public third-party data is the exception
  (`examples/public/`, ADR-020).

## What this is
1. A standalone, client-side Parquet viewer + SQL editor in a single `index.html`: no
   backend, no build step, no package.json. It must keep working both opened via `file://`
   (double click) and served statically. Main objective.
2. Tools to build the metadata that feeds an AI agent so it can write queries without
   seeing the data: stamp the metadata into the parquets and check it against a YAML
   contract, verify the declared keys (PKs, FKs, uniques) against the data, compute the
   table stats (`docs/model/metadata_model.md`).

## Architecture

### html
`index.html`: styles, markup and a single `<script type="module">`. Stack, code map and
limits: `docs/html/viewer.md`. Develop by opening it in Chrome/Edge, by double click and
served (`python -m http.server`): load a `.parquet`, run a query, try both exports (CSV,
XLSX) (`viewer.md` §7).
- **DuckDB-Wasm** comes from a CDN (jsDelivr) as an ES module, not vendored: Chrome blocks
  local relative module imports over `file://` but allows cross-origin CDN imports. Do not
  split the script into local ES modules: it breaks the double click (ADR-006).
- SheetJS, Leaflet and Chart.js are classic `<script>` tags for the same reason.
- All processing is local: files never leave the browser, no server by design (ADR-007).

**GOVERNANCE RULE**: NO DATA leaves the tenant, only metadata: no row ever leaves. The
`mechanical` stats are metadata with real values (`min_max`, `fk_orphans`); they may go to
the agent, and whether that is acceptable is each deployment's call (ADR-019).

### python
Install with `pip install -e ".[dev]"` (src layout). `src/meta_tools/` is the only
installable package; `scripts/` holds runnable scripts, never imported by the package (only
`project_env.py` is imported, by the other scripts); `tests/` holds the pytest suite.
Imports inside the package are always relative (`from .contract import ...`).

Organized by **criticality first**, then by group of the metadata model (ADR-009), with
module names in the contract's vocabulary. Functions of each module: the docstring of
`src/meta_tools/__init__.py` and each module's `__all__`.
- `write/` - **critical**: what a producer ETL in another repo imports to stamp a table
  (`parquet.py`, `provenance.py`). Nothing else is required to write metadata.
- `mechanical.py` - group 1 (`ParquetScanner`): stats + verification of the declared keys.
- `check/` - checking against the contract, not required to write: `contract.py` (the only
  place that knows where the contract lives), `sources.py` (readers of the surfaces where
  metadata lives; they do not validate), `schema.py` (the generic dict-vs-contract engine),
  and the checkers that pick a sub-tree of it: `authoring.py` (groups 2+3), `provenance.py`
  (5), `mechanical.py` (1), `inspect.py` (4).
- `etl.py` - building blocks of the pipeline; the package reads no env vars, the caller
  injects paths. `build.py` - the agent artifacts (ADR-014). `fields.py` - field names.
- `meta_contract.yaml` - package data, single copy (none at the repo root).

Group 4 (`inspect`) is not produced by the package: an external agent writes it
(`/inspect-table`, not built yet).

Outside the package:
- `scripts/run_metadata_etl.py` - stage 1, driven by an ETL config (`config/etl.yaml` by
  default; template `config/etl.example.yaml`) whose paths resolve through `.env`
  (`scripts/project_env.py`, which does not import `meta_tools`). `docs/model/etl_strategy.md`.
- `scripts/build_reading_key.py` - stage 2: regenerates `reading_key.yaml` (committed) from
  the contract. Stage 3 (publishing to a consumer) is deployment-specific: no public script.
- `tests/test_contract.py` - the suite, incl. the contract's self-consistency test (ADR-005);
  `tests/test_example_dataset.py` - the example dataset against the contract.
- `examples/public/cauchari_ni43101/` - example dataset from a public third-party NI 43-101
  report (ADR-020): CSVs, stamped parquets, `inspect` sidecars and the ETL outputs (config
  `etl.sampledata.yaml`, env var `SAMPLEDATAPATH`), with its own build scripts. Its files are
  test data: regenerate them (its `DATASET.md`) whenever its metadata, the contract or the
  writer change.

## Maintaining coherence
- The viewer consumes the tables and metadata the python side creates; the agent joins both.
  When a field's `agent_rule` or `value_descriptions` changes, regenerate `reading_key.yaml`
  (`scripts/build_reading_key.py`). What the agent reads, and why: ADR-014, ADR-019.
- The checkers are agnostic to the contract's content; the ETL config and `ParquetScanner`
  are not: their output must stay consistent with the contract (testable with a dry run).
  Test, or ask the user, when either changes.
